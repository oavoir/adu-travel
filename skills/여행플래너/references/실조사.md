# 실조사 — 진짜로 찾아오는 절차

상담으로 "무엇을 찾을지"가 정해졌으면, 이제 **실제로 나가서 찾아온다.** 아는 걸로 채우거나 그럴듯하게 지어내면 안 된다. 이 문서는 매 여행마다 실행하는 조사 프로토콜이다.

**원칙: 일정에 들어가는 모든 장소는 이번 세션에서 실제로 확인한 것이어야 한다.** 기억으로 쓴 식당 이름은 폐업했을 수 있고, 영업시간은 바뀌었을 수 있다.

## 1. 조사 계획 — 뭘 몇 개 찾아야 하는가

상담 결과를 매트릭스로 펼친다. 이게 조사 대상 목록이다.

```
여행 3박 4일 · 부모님 동행 · 맛집 중심 · 대중교통
→ 필요 끼니: 점심 4 + 저녁 4 = 8
   후보는 필요량의 2배 확보 (휴무·만석 대비)           → 식당 후보 16곳
→ 필요 관광: 하루 2곳 × 4일 = 8곳, 후보 1.5배          → 관광 후보 12곳
→ 지역 클러스터: 숙소 기준 3~4개 권역
→ 어르신 조건: 좌식 없음 · 도보 짧음 · 대기 없음 · 이른 저녁
```

**후보를 넉넉히 잡는 이유**: 조사해보면 절반이 탈락한다. 휴무일이 겹치고, 그날 동선에서 멀고, 예약이 필요하고, 좌식이라 어르신이 못 앉는다. 필요량만 찾으면 반드시 다시 조사하게 된다.

## 2. 소스 결정 — DB에 있으면 DB, 없으면 직접 찾아낸다

### 2-1. `국가별플랫폼.md`에 항목이 있는 나라

거기 적힌 A등급 소스로 바로 간다. 점수 척도와 막힌 사이트 목록도 그대로 쓴다.

### 2-2. 없는 나라·지역 — 프로브 절차

**추측하지 말고 실제로 두들겨서 알아낸다.** 6단계다.

**① 후보 발굴** — 그 나라에서 뭘 쓰는지 찾는다

- `<나라> 맛집 사이트 현지인` / `best restaurants <city> local guide` 검색
- 이웃 나라 플랫폼이 커버하는지 확인 (OpenRice는 여러 아시아 시장, TheFork는 유럽 다수)
- 국가 단위 레스토랑 가이드가 있는지 (미슐랭 외에 자국 가이드가 있는 나라가 많다)
- 공식 관광청, 현지 신문·매거진의 best-of 기사

**② 접근성 프로브** — 후보마다 **실제 상세 페이지를 하나 fetch한다**

- ⚠️ 홈페이지 말고 **식당 상세나 도시 리스트 페이지**로 테스트한다. 홈은 열리는데 상세가 막힌 사이트가 흔하다
- 판정: `읽힘` / `로그인벽` / `봇차단(HTTP 코드)` / `빈껍데기(JS 셸)` / `DNS 사망` / `404`
- **fetch 안 해본 후보는 "미검증"이지 "됨"이 아니다**

**③ 필드 확인** — 읽히는 게 있으면 뭐가 나오는지 본다

- 이름·점수·리뷰수·주소·영업시간·정기휴무·가격대·전화·결제수단·예약 여부
- 이름만 나오면 후보 목록용이고, 영업시간·휴무까지 나오면 일정 조립에 바로 쓸 수 있다. 이 차이가 크다

**④ 척도 확인** — 점수가 있으면 **만점이 몇 점인지 반드시 확인한다**

- 4~5곳을 샘플링해서 분포를 본다
- 상위권이 3점대에 몰리면 압축된 척도(일본 타베로그형), 9점대가 보이면 10점 만점(베트남 푸디형)
- **이걸 틀리면 조사 전체가 무의미해진다**

**⑤ 생존 확인** — 살아있는지 본다

- 최근 콘텐츠 날짜, 푸터 저작권 연도, 경쟁사로 리다이렉트되는지, 종료 공지가 있는지
- 실제로 DB 작성 중에 죽은 서비스가 여럿 나왔다 (망고플레이트 DNS 사망, Quandoo 2026년 종료 공지, 대만 아이핑 DNS 사망). **살아있다는 증거를 보기 전엔 죽은 것으로 간주한다**

**⑥ 폴백** — 로컬 플랫폼이 하나도 안 읽히면 범용 소스로 간다 (3절)

**프로브 결과는 반드시 사용자에게 한 줄로 보고한다.** "이 나라는 로컬 맛집 플랫폼이 없어서 현지 매체 기사와 위키보이지 기준으로 찾았다"는 말이 신뢰를 만든다.

## 3. 범용 폴백 — 어느 지역에서도 되는 것

로컬 소스가 없어도 이건 된다. **실측으로 확인된 것만 적는다.**

| 소스            | URL 형식                         | 비고                                                |
| :-------------- | :------------------------------- | :-------------------------------------------------- |
| **Wikivoyage**  | `en.wikivoyage.org/wiki/<Place>` | **가장 안정적. 403이 없다.** 식당명·주소·가격대까지 |
| Wikivoyage 구역 | `.../wiki/<City>/<District>`     | **대도시는 본문이 잘리니 반드시 구역 문서로**       |
| 공식 관광청     | 나라마다 다름                    | 권역 분류·계절 정보에 강함. 일부는 403              |
| Time Out        | `timeout.com/<city>/restaurants` | 커버 도시만. **없으면 404**                         |
| World's 50 Best | `theworlds50best.com/list/1-50`  | 지역판도 있음                                       |
| trip.com        | `trip.com/hotels/list?city=<id>` | 숙소 시세. `<title>`로 도시 검증 필수               |
| DuckDuckGo lite | `lite.duckduckgo.com/lite/?q=`   | 차단 플랫폼의 점수·순위를 스니펫으로 회수           |

**Wikivoyage 실측 결과** — 리스본 구역 문서, 루앙프라방, 트빌리시, 제주 전부 정상적으로 읽혔다. 소도시·섬처럼 플랫폼 데이터가 얇은 곳에서는 이게 사실상 유일한 구조화 소스다. 대도시만 본문이 잘리므로 그때만 구역 문서로 내려간다.

## 4. 실행 — 실제로 긁는다

### 병렬로 던진다

지역 클러스터가 3~4개면 각 지역 조사를 **한 번에 병렬로** 실행한다. 하나씩 순차로 하면 사용자를 오래 기다리게 한다.

### 스크래치 파일에 즉시 누적한다

**세션이 길어지면 앞쪽 조사 결과가 컨텍스트에서 날아간다.** 반드시 파일에 쌓는다.

```markdown
## 조사결과.md

### 식당

| 이름 | 지역 | 점수 | 영업시간                 | 정기휴무 | 전화   | 예약      | 결제     | 출처 URL           |
| :--- | :--- | :--- | :----------------------- | :------- | :----- | :-------- | :------- | :----------------- |
| ...  | ...  | 3.49 | 11:30-15:00, 17:00-22:00 | 월       | 03-... | 디너 필수 | 카드가능 | tabelog.com/en/... |

### 미확인 항목

- OO식당: 이름만 확보, 영업시간 못 찾음 → 일정에 넣으려면 추가 확인 필요
```

**출처 URL을 반드시 남긴다.** 나중에 사용자가 "이거 진짜야?"라고 물으면 그 자리에서 답할 수 있어야 한다.

### 조사량 기준

- 3~~4박이면 식당 상세 조사 12~~16곳, 관광 8~12곳이 적정선
- 그 이상은 시간과 예산만 쓰고 일정에 안 들어간다
- 그 이하면 휴무·동선으로 탈락했을 때 대체가 없다

## 5. 검증 — 후보를 일정에 넣기 전에

수집한 후보 하나하나에 대해 확인한다. **아래 넷은 확인 없이 일정에 넣지 않는다.**

| 확인 항목                 | 왜                                                                                    |
| :------------------------ | :------------------------------------------------------------------------------------ |
| **실존·현재 영업**        | 폐업했을 수 있다. 최근 리뷰 날짜나 플랫폼의 폐업 표시를 본다                          |
| **여행 요일의 영업 여부** | 정기휴무를 여행 날짜와 직접 대조한다. 목요일 휴무를 목요일에 넣는 게 가장 흔한 사고다 |
| **그날 동선 위에 있는지** | 좋은 식당이라도 반대편이면 못 간다                                                    |
| **상담 조건 충족**        | 어르신인데 좌식인지, 아이인데 대기가 긴지, 혼자인데 2인 이상만 받는지                 |

추가로 상황에 따라: 브레이크타임, 예약 필요 여부와 방법, 현금 전용인지, 식이 제한 대응 메뉴가 있는지.

**확인 못 한 항목은 "미확인"으로 표시해서 일정에 넣거나, 아예 뺀다.** 확인한 척하지 않는다.

## 6. 커버리지 자가 점검 — 일정을 내밀기 전에

조립을 끝냈으면 스스로 점검한다. 하나라도 걸리면 조사로 돌아간다.

```
□ 모든 날의 점심·저녁에 배정된 곳이 있는가
□ 각 배정에 휴무 대비 백업이 하나씩 있는가
□ 모든 장소의 영업시간을 이번 세션에서 확인했는가
□ 여행 요일과 정기휴무를 실제로 대조했는가
□ 예약 필요한 곳을 표시하고 방법(전화번호·링크)까지 줬는가
□ 상담에서 나온 조건(동행자·페이스·무게중심)이 실제로 반영됐는가
□ 출처 URL이 전부 남아 있는가
□ 못 찾은 것을 못 찾았다고 표시했는가
```

## 7. 사용자에게 보고하는 법

조사가 끝나면 **뭘 얼마나 확인했는지** 한 문단으로 말한다. 이게 "진짜 찾아봤다"는 증거다.

> "타베로그에서 아사쿠사·긴자·신주쿠 세 지역 상위권을 훑어서 식당 16곳을 봤고, 그중 어르신 모시기 괜찮은 곳(좌식 아니고 대기 없는 곳) 9곳을 골랐어요. 영업시간이랑 정기휴무는 전부 확인했는데, 한 곳은 여행 가시는 목요일이 휴무라 뺐습니다. 관광지는 도쿄 관광청 권역 분류로 나눠서 12곳 보고 8곳 남겼어요."

**숨기지 않는다.** 못 읽은 소스가 있으면 밝히고, 커버리지가 얕으면 얕다고 말한다.

## 8. 하지 말 것

- **기억으로 식당 이름을 쓰는 것.** 이번 세션에서 확인 안 한 곳은 일정에 못 들어간다
- **영업시간·가격·소요시간을 추정으로 채우는 것**
- 랭킹 상위를 그대로 나열하는 것 — 상담 조건으로 걸러야 한다
- 막힌 사이트를 계속 재시도하는 것 (토큰과 시간만 태운다)
- 프로브 없이 "이 나라는 이걸 쓸 것"이라고 단정하는 것
- 조사 결과를 스크래치에 안 쌓고 대화 기억에만 두는 것
