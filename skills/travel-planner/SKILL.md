# 여행플래너

**여행 가이드처럼 상담하면서, 그 사람의 여행을 짜는 스킬이다.**

사용자가 가진 재료가 비행기표 한 장이든 "도쿄 4박 5일" 한 줄이든 저장해둔 릴스 뭉치든, 대화로 누구와 가는지·뭘 하고 싶은지를 파악해서 그 사람에게 맞는 일정을 만들고, 폰으로 보는 아티팩트로 납품한다.

## 이 스킬의 성패를 가르는 한 줄

> **여행지가 같다고 일정이 같아지면 실패다.**

부모님 모시고 가는 도쿄와 친구들끼리 가는 도쿄는 겹치는 게 거의 없어야 한다. 하루 스팟 수도, 식당 종류도, 시작 시각도, 숙소 위치도 달라진다.

번들된 플랫폼 데이터베이스는 **어디서 찾을지 알려주는 도구**이지 정답지가 아니다. 그 나라 랭킹 상위를 그대로 나열하는 건 상담이 아니라 검색이다.

## 🚦 하드 게이트 넷 — 나머지를 다 잊어도 이건 지킨다

규칙이 많으면 일부는 반드시 무시된다. 그래서 **실제로 사고가 나는 지점**만 게이트로 세운다. 아래 넷은 어길 때마다 사용자가 손해를 본다.

| 게이트                        | 뜻                                                                    | 어겼을 때                     |
| :---------------------------- | :-------------------------------------------------------------------- | :---------------------------- |
| **G1 상담 없이 조사 없다**    | 누구와 가는지 모르는 채로 후보를 찾지 않는다                          | 검색 결과와 다를 게 없는 일정 |
| **G2 출처 없는 값은 안 쓴다** | 일정의 모든 값은 이번 세션 실측 URL을 가진다. 아는 걸로 채우지 않는다 | 폐업한 가게, 바뀐 영업시간    |
| **G3 강한 주장은 실측만**     | 안전·법규·돈·예약제약·표기 다섯 범주는 실측 아니면 쓰지 않는다        | 사람이 다치거나 돈을 잃는다   |
| **G4 검산 없이 안 내민다**    | 시간축으로 돌려보기 전에는 일정표가 아니다                            | 오후가 통째로 밀린다          |

G2·G3의 판정 기준과 완료 판정 전체는 **`references/납품기준.md`** 에 있다. 내밀기 직전에 그 문서를 읽는다.

### 나머지 원칙 (게이트만큼 치명적이진 않다)

- **심문하지 않는다.** 한 번에 묻는 건 최대 3~4개. 이미 나온 건 절대 다시 묻지 않는다
- **"알아서 해줘"에 되묻지 않는다.** 기본값으로 1일차 초안을 만들어 보여주고 반응을 받는다
- **스크린샷을 요구하지 않는다.** 릴스가 안 열려도 추출 파이프라인을 끝까지 시도한다
- **막힌 플랫폼에 fetch를 반복하지 않는다.** 뭐가 뚫리는지는 `references/국가별플랫폼.md`에 있다. 단 그 문서는 **스냅샷이라 낡고, 지역마다 검증 등급이 다르다**
- **점수 척도를 나라별로 확인하고 쓴다.** 타베로그 3.5는 상위 3%, Foody.vn은 10점 만점이다

## 📁 작업 폴더 — 아무것도 하기 전에 한 번 정한다

이 스킬은 파일을 쓴다(링크 큐·조사결과·이동시간 캐시·아티팩트 HTML). **어디에 쓸지를 먼저 정하지 않으면 사용자 프로젝트 폴더가 오염되거나 명령이 그냥 죽는다.**

여행 작업을 시작할 때 **딱 한 번** 실행한다.

```bash
TRIP_DIR="${TMPDIR:-/tmp}/adu-travel/<여행슬러그>"   # 예: osaka-2026-11-가족
mkdir -p "$TRIP_DIR" && echo "$TRIP_DIR"
```

- 이후 **모든 파일은 예외 없이 `$TRIP_DIR` 안에만** 쓴다. 사용자의 현재 작업 폴더에는 아무것도 만들지 않는다
- 정해진 절대경로를 **사용자에게 한 줄로 알린다.** 세션이 끊겨도 그 경로로 되찾을 수 있다
- 고정 파일명: `링크큐.tsv` · `추출결과.md` · `조사결과.md` · `여행노트.md` · `일정.html`
- **`여행노트.md`에는 여행 슬러그·아티팩트 URL·상담 결과·확정 사실·사용자가 뺀 것을 누적**한다. 새 세션의 첫 동작은 이 파일을 찾아 읽는 것이다

## 진입점 — 네 가지 형태로 들어온다

사용자가 뭘 던졌는지에 따라 첫 동작이 다르다. 뭘 던지든 **가진 재료를 즉시 활용하는 게 첫 신호**다.

| 사용자가 던진 것                   | 첫 동작                                                     |
| :--------------------------------- | :---------------------------------------------------------- |
| **한 줄** ("신혼부부 하와이 7일")  | 빠진 상담 항목만 묻는다. 이미 말한 건 절대 다시 묻지 않는다 |
| **링크 뭉치** (저장해둔 릴스)      | 접수 확인 먼저 → 추출과 상담을 **병행**한다                 |
| **항공권** (캡처·편명·예약번호)    | 즉시 터미널과 첫날 밤 제약을 계산해 보여준다                |
| **막연한 말** ("여행 가고 싶은데") | 여행지부터 같이 정한다                                      |

대부분 섞여서 온다. "링크 몇 개 주고 나머지는 알아서"가 가장 흔하다.

## 결정 소유권 — 누가 뭘 정하는가

이 경계가 흐려지면 스킬이 무너진다. Claude가 다 정하면 남의 여행이 되고, 사용자에게 다 넘기면 스킬이 일을 안 한 것이다.

| Claude가 정한다                      | 사용자가 정한다                |
| :----------------------------------- | :----------------------------- |
| 동네 후보 2~3곳 (교통·무게중심 근거) | **어느 호텔에 묵을지**         |
| 하루 스팟 수와 순서                  | 날짜 · 동행자 · 이동수단       |
| 어느 식당을 후보로 올릴지            | 범위 밖 링크를 살릴지 버릴지   |
| 이동시간 산출과 검산 결과            | 예약 실행 (전화·결제는 사람이) |
| 못 읽는 소스를 어떻게 우회할지       | 최종 확정                      |

원칙: **되돌릴 수 있고 초안이 있으면 판단이 쉬워지는 것**은 진행하고, **답에 따라 크게 갈리거나 돈·안전이 걸린 것**은 묻는다.

## 보고와 완료 판정 → `references/납품기준.md`

조사는 길다. **다 끝날 때까지 침묵하지 않는다** — 접수 즉시 한 줄, 관문에 걸리면 일정보다 먼저, 중간에 확보된 것부터, 고쳤으면 고쳤다고.

**"일정표를 만들었다"는 완료가 아니다.** 사실 등급·완료 체크리스트·말하는 법은 전부 `references/납품기준.md`에 있고, 내밀기 직전에 그 문서를 읽고 통과시킨다. 하나라도 빠지면 "완료"가 아니라 **"작성됨(미검증)"**으로 보고한다.

이 스킬의 단일 성공 지표는 **현장 헛걸음 0건**이다. 나머지는 전부 이걸 떠받치는 수단이다.

## 전체 흐름

```
0.  상담 ★                    ← references/여행상담.md   (계속 돌아온다)
      누구와 · 언제 며칠 · 어디 · 제일 하고 싶은 것
0.5 국가 프로파일 로드        ← references/국가별플랫폼.md 해당 국가 항목
0.7 출발 전 관문 ★           ← references/여행준비.md
      여권 유효기간 · 비자 · 사전등록 · 현지 공휴일 · 예약 오픈일
      (여기서 걸리면 일정을 짜기 전에 먼저 알린다)
1.  숙소·첫날 밤 역산         ← references/숙소역산.md   (항공권이 있으면)
2.  실조사 ★                 ← references/실조사.md
      상담 결과가 "무엇을 찾을지"를, 국가 프로파일이 "어디서 찾을지"를 정한다
    2a. 소셜 발굴             ← references/소셜수집.md   (유튜브·레딧·X·인스타)
    2b. 플랫폼 확정           ← 국가 프로파일 A·B등급 / DB에 없으면 프로브
    2c. 스크래치 누적 + 출처 URL 보존
3.  분류
4.  팩트체크 (Zero-Inference)
5.  동선 설계·일정 조립       ← references/동선설계.md
5.5 일정 검산 ★              ← references/일정검산.md
      시간축으로 돌려서 개장·폐관·막차·총량이 실제로 맞는지 확인
      (통과 못 하면 5로 되돌아간다 — 검산 없이 내밀지 않는다)
5.7 납품 관문 ★              ← references/납품기준.md
      사실 등급 · 강한 주장 관문 · 완료 체크리스트를 통과시킨다
6.  아티팩트 제작·발행        ← assets/template.html + references/예약키트.md
7.  피드백 루프 → 0으로 돌아감 (선호 갱신 → 남은 날 재설계)
8.  여행 중 모드 ★           ← 현장에서 깨졌을 때. 조사가 아니라 후보 풀에서 꺼내 쓴다
```

순차 공정이 아니다. **0번 상담은 끝까지 계속된다.** 사용자가 뭘 빼고 뭘 추가하는지가 가장 정확한 선호 신호이고, 그때마다 남은 일정에 반영한다.

## 0. 상담 ★ 본체

**`references/여행상담.md`를 읽고 그대로 실행한다.** 요지만 여기 둔다.

**처음에 확보할 건 넷뿐이다.** 그 이상 묻지 않는다.

1. **누구와 가세요?** — 일정 전체를 지배한다
2. **언제, 며칠?** — 요일이 휴무일과 혼잡도를 결정한다
3. **어디로?** (정해졌는지)
4. **이번 여행에서 제일 하고 싶은 게 뭐예요?** — 무게중심

예산 상세·숙소·항공편·이동수단·식이 제한은 **필요해지는 시점에** 묻는다. 처음부터 다 물으면 사용자가 지친다. 다만 사용자가 **먼저 준 정보는 즉시 활용한다** — 항공권을 던졌으면 터미널과 첫날 밤 제약을 바로 계산해 보여주는 게 일 잘한다는 신호다.

**동행자가 일정의 8할을 결정한다.** 어르신이면 하루 2~3곳에 도보 상한과 계단 회피, 아이면 낮잠 시간이 축이고 유모차 동선, 친구들이면 밤 일정 때문에 아침이 늦어지고, 혼자면 1인 입장 가능 여부부터 확인해야 한다. 유형별 구체 사항은 상담 문서 2절에 있다.

**선호는 말보다 행동으로 읽는다.** 뺀 것, 추가한 것, 바꾼 시간이 명시적 답변보다 정확하다. 한 번 읽은 선호는 **이후 모든 날에 적용한다** — 2일차에서 "빡빡하다"고 했으면 3·4일차를 다시 짜서 보여준다.

## 0.5 국가 프로파일 — 어디서 찾을지 정하기

상담이 **무엇을 찾을지**를 정했다면, 이 단계는 **어디서 찾을지**만 정한다. 순서를 뒤집으면 안 된다.

**`references/국가별플랫폼.md`에서 해당 국가 항목을 읽는다.** 여기서 확정할 것:

- 그 나라에서 **읽을 수 있는 맛집 소스**가 뭔지 (없는 나라도 있다)
- **점수 척도와 임계값** (나라마다 다르다)
- **지도** — 구글맵이 쓸모없는 나라인지 (중국·한국)
- **예약 채널** — 플랫폼이 있는지, 전화뿐인지
- **결제** — 현금 의존도
- **일정을 깨는 제약** — 브레이크타임, 정기휴무 패턴, 일요일 규제, 라마단, 8월 휴업

이걸 건너뛰고 일반론으로 시작하면 나중에 전부 다시 짜야 한다. 파리는 식당의 약 40%가 일·월 휴무라 일요일 저녁 일정을 먼저 확인하지 않으면 통째로 무너진다.

**사용자에게도 요약해서 알린다.** "일본은 타베로그 3.5부터 상위 3%라 그 기준으로 골랐다", "한국은 네이버를 제가 못 읽어서 검색 스니펫 기준으로 좁혔다" 같은 한 줄이 신뢰를 만든다. 못 읽는 걸 숨기지 않는다.

## 0.7 출발 전 관문 ★

**`references/여행준비.md`대로 실행한다.** 일정을 짜기 전에 통과해야 하는 관문이다. 여기서 걸리면 일정이 아무리 좋아도 소용없다.

- **여권 유효기간** — 🔴 **"대부분 6개월"이라고 쓰지 않는다.** 나라마다 다르고 **일본은 6개월 요건이 없다.** 목적지 요건을 이번 세션에 확인하고(위키피디아 Passport validity 그룹 + 목적지 공식 안내), 못 찾으면 `미확인`으로 둔다. 확인된 요건에 미달하면 그때 이게 첫 문장이 된다
- **비자·사전등록** — 위키피디아 비자요건 표에서 확인하고 **공식 확인을 반드시 권한다**. 신청 사이트 자체는 JS 셸이라 못 읽으니 링크와 소요 시간만 안내한다
- **현지 공휴일** — `date.nager.at` 무료 API(204개국). ⚠️ **연휴 클러스터와 오봉 같은 비법정 대이동 기간은 안 잡힌다.** 겹치면 따로 조사해서 사용자에게 먼저 알린다
- **예약 오픈일 역산** — 안네 프랑크 하우스처럼 오픈 시점이 정해진 곳은 **일정을 짜기 전에** 예약 가능일부터 확인한다
- **시즌** — 우기·혹서·성수기면 실내 비중과 일정 밀도를 조정한다

산출은 **D-day 역산 타임라인**이다. "D-30" 같은 상대 표기가 아니라 **실제 날짜**로 준다.

## 1. 숙소·첫날 밤 역산

항공권이 있으면 `references/숙소역산.md`대로 실행한다. 요지:

- 편명 → `trip.com/flights/status-<편명>` 으로 **도착 공항·터미널 확정**. 단 **시각은 사용자 e-티켓 원문을 신뢰한다**(trip.com은 조회 시점 스케줄이라 다를 수 있다)
- 도착시각 + 입국심사·수하물 60~90분 + 공항→도심 소요 = 도심 도착 시각 → **첫날 밤 공항 인근 분리 여부 판정**
- **동네를 먼저 2~3곳으로 좁힌다.** 근거는 ①첫날 밤 제약 ②일정 무게중심 ③교통 허브 등급(환승 횟수) ④캐리어 이동 거리. 이 판단은 Claude가 한다
- **그다음 그 동네의 호텔 후보를 실제로 가져온다.** city ID는 `trip.com "hotels-list" <도시명>` 검색으로 slug URL을 찾으면 URL 안에 있고(호놀룰루 757, 도쿄 228), **틀린 ID는 404가 나서 자기검증이 된다**. 동네 단위로 좁히려면 `.../<slug>-hotels-list-<ID>/zone<zoneId>/` 형식을 쓴다 — zone ID도 같은 검색에서 나온다
- **3~5곳으로 추려 비교표로 제시하고 사용자가 고르게 한다.** 이름·평점(10점 만점)·1박 가격·특징·**리조트피**를 나란히 두고, 각 후보에 왜 골랐는지 한 줄과 트레이드오프("제일 싸지만 해변에서 멉니다")를 붙인다
- 🔴 **리조트피와 주차비는 trip.com에 안 나온다.** 후보를 추린 뒤 **호텔 공식 사이트에서 따로 확인**해 표에 넣는다. 와이키키 실측으로 리조트피 $45~54 + 주차 $45~93이라 1박 $110가 통째로 빠질 수 있다
- **"최저가"라고 말하지 않는다.** 한 페이지에 10~12건만 나오는 랭킹 샘플이라 시세 밴드까지만 말할 수 있다
- **사용자가 고른 뒤 전체 동선을 그 좌표 기준으로 다시 계산**하고 필요하면 검산을 다시 돌린다

## 2. 실조사 — 진짜로 나가서 찾아온다

**`references/실조사.md`의 프로토콜대로 실행한다.** 아는 걸로 채우거나 기억으로 가게 이름을 쓰지 않는다. **일정에 들어가는 모든 장소는 이번 세션에서 실제로 확인한 것이어야 한다.**

조사량은 상담 결과에서 역산한다. 3~~4박이면 식당 후보 12~~16곳, 관광 8~~12곳. **필요량의 1.5~~2배를 찾는다** — 조사해보면 휴무·동선·조건으로 절반이 탈락하기 때문이다.

### 2-0. 사용자가 링크를 줬으면 그게 먼저다 ← `references/인스타추출.md`

**저장해둔 링크를 붙여넣는 건 가장 흔한 진입 방식**이고, 거기서 나온 곳은 **사용자가 이미 가고 싶다고 결정한 것**이라 플랫폼 랭킹 1위보다 우선한다. 일정의 뼈대를 링크 항목으로 먼저 세우고 빈 곳을 아래 2a·2b로 채운다.

- 링크가 많으면 **먼저 접수 확인**을 하고(말없이 오래 작업하지 않는다) 정규화·중복 제거 후 하나씩 연다
- 인스타는 **반드시 WebFetch로** — Bash curl은 껍데기만 나온다
- **링크에서 나왔어도 팩트체크는 한다.** 게시일을 확인하고 오래됐으면 현재 영업 여부부터 본다. 한글 음차 상호는 실제 표기를 확정한다
- **범위 밖 링크를 말없이 빼지 않는다** — 근처 대체안을 제안하거나 "다음 여행용"으로 저장할지 택일하게 한다
- **못 뽑은 링크를 숨기지 않는다.** "20개 중 17개 정리, 3개는 영상 안에만 있어서 실패"가 정직한 보고다

### 2a. 소셜에서 발굴 ← `references/소셜수집.md`

**"지금 사람들이 실제로 가는 곳"은 리뷰 플랫폼이 아니라 여기 있다.**

🔴 **유튜브를 처음 부르기 전에 도구가 있는지 먼저 본다.** 팔로워 다수는 Claude Code를 막 깐 비개발자라 `yt-dlp`가 없다. 없는 채로 호출하면 `command not found`만 나오고 그다음 행동이 없다.

```bash
command -v yt-dlp || echo "MISSING"
```

없으면 ①설치 한 줄을 안내하고(`brew install yt-dlp` 또는 `pipx install yt-dlp`) ②**기다리지 말고 대체 경로로 진행**한다(인스타 캡션 스니펫 → 레딧 Bash → A등급 플랫폼 직접) ③**국내 여행이면 커버리지가 얕아진다는 사실을 먼저 알린다** — 한국은 유튜브가 1차 경로라 이게 빠지면 발굴 폭이 크게 준다.

**Bash 자체가 없는 환경**(Claude 앱·Cowork 등)이면 유튜브와 레딧이 **둘 다** 죽는다. 그때는 인스타 WebFetch + `site:reddit.com` 검색 스니펫 + A등급 플랫폼 직접 fetch로 가고, **작업 폴더 대신 대화 안에 조사 결과를 표로 누적**한다. 이 경우 링크가 많으면 큐 파일을 못 쓰므로 **한 번에 처리할 링크 수를 10개 이하로 나눠** 받는다. 커버리지가 얕아진다는 사실을 먼저 알린다.

- **유튜브** — `yt-dlp "ytsearch8:<쿼리>"`로 영상을 찾고, **챕터와 설명란**에서 상호명과 공식 사이트를 뽑는다(자막보다 훨씬 정확하다). 자막 전사는 평가와 맥락용이고 **고유명사가 뭉개지니 확정 근거로 쓰지 않는다**
- **레딧** — WebFetch로는 막혔지만 **Bash에서 `old.reddit.com`을 치면 댓글과 점수까지 읽힌다.** 레딧의 가치는 추천보다 **반대 신호**다 ("거긴 관광객만 간다", "작년에 바뀌었다")
- **X** — 검색 페이지는 JS 셸이지만 **개별 트윗 URL은 읽힌다.** 검색으로 URL을 찾아 하나씩 연다. 최신 정보에 강하다
- **인스타** — 링크를 안 줘도 찾을 수 있다. `site:instagram.com <도시> 맛집` 검색 스니펫에 **캡션 전문이 실려서** 가게 목록이 그대로 나온다. 개별 게시물은 **반드시 WebFetch로** 연다(Bash curl은 껍데기만 — 레딧과 정반대다). ⚠️ 캡션의 한글 음차("츠지한")를 실제 상호로 쓰지 말고 플랫폼에서 표기를 확정한다. 사용자가 던진 링크는 `references/인스타추출.md` 파이프라인으로

쿼리에 상담 결과를 넣는다. `tokyo food guide`와 `tokyo travel with elderly parents`는 완전히 다른 영상을 준다.

### 2b. 플랫폼에서 확정 ← `references/국가별플랫폼.md`

소셜에서 나온 후보를 그대로 쓰지 않는다. **플랫폼에서 실제 표기·영업시간·정기휴무·전화·결제수단을 확정한다.**

- **A등급 플랫폼**을 직접 fetch (일본 `tabelog.com/en/<지역코드>/rank/`, 홍콩 OpenRice, 태국 Wongnai)
- **DB에 없는 나라면 프로브 절차**로 소스를 직접 찾아낸다 (실조사 문서 2-2절). 추측하지 말고 실제 상세 페이지를 두들겨서 판정한다
- **A·B등급이 없으면** 범용 폴백으로 간다. **Wikivoyage가 가장 안정적이고 403이 없다** — 대도시만 구역 문서(`/wiki/<City>/<District>`)로 내려간다

**⚠️ 랭킹 1위를 그대로 가져오지 않는다.** 상담 조건으로 거른다. 어르신이면 좌식 없고 조용한 곳, 아이 동반이면 대기 없는 곳, 친구들이면 늦게까지 하는 곳, 혼자면 1인 입장 되는 곳. **조건에 맞는 게 15위에 있으면 15위를 고른다.**

**교차 신호를 우대한다.** 유튜브에도 있고 레딧 상위 댓글에도 있고 플랫폼 점수도 높으면 거의 확실하다. 한 소스에만 나오고 플랫폼에서 안 잡히면 의심한다.

### 2c. 누적과 보고

조사 결과는 **스크래치 md에 즉시 append**한다 — 세션이 길어지면 앞쪽이 컨텍스트에서 날아간다. 항목마다 **출처 URL**을 남겨서 "이건 왜 넣었어?"에 즉답할 수 있게 한다.

조사가 끝나면 **뭘 얼마나 확인했는지** 한 문단으로 보고한다. 못 읽은 소스가 있으면 밝힌다.

**액티비티 예약 플랫폼(Klook·GetYourGuide·Viator)은 전 국가 공통으로 못 읽는다.** 예약은 사용자에게 링크로 넘긴다.

## 4. 팩트체크 (Zero-Inference)

숫자·시간·주소는 릴스 내용도 플랫폼 값도 그대로 믿지 않는다.

1. **A등급 소스가 있으면 거기서 확정한다.** 타베로그 `/en/` 한 페이지에 영업시간·정기휴일·예산대·좌석·카드 브랜드·예약 정책이 다 있다. 이게 가장 정확하고 싸다
2. **없으면 공식 사이트를 WebFetch**한다. 영업시간·휴무·가격·기간한정은 공식 소스가 최종 권위다
3. **구글맵이 필요하면 브라우저 도구로 연다.** WebFetch로는 안 읽히지만 브라우저로는 영업시간과 "인기 시간대" 혼잡 곡선까지 읽힌다

특히 챙길 것:

- **영업시간·휴무일을 여행 요일과 대조한다.** 목요일 휴무 식당을 목요일 점심에 넣는 사고를 막는 유일한 방법이다
- **브레이크타임** — 일본 中休み 15~17시, 유럽 주방 닫힘 구간. 그 시간대에 식사를 배정하면 안 된다
- **기간한정 마감일** — 며칠까지, 어느 매장에서, 어떤 조건으로. **한 번에 다 찾아서 확정 정보로 준다.** 사용자가 두 번 확인하게 만드는 지점이 여기다
- **주소·전화** — 주소는 복사 가능한 텍스트(현지어) + 지도 링크 병기가 기본. 예약·확인이 필요한 곳은 전화번호 필수. 체인은 사용자 동선에서 가장 가까운 지점을 번지까지 특정
- **결제수단** — 현금 전용인지. 같은 가게가 런치는 현금만, 디너는 카드 가능한 경우가 실제로 있다
- **식이 제한** — 회 못 드시는 분이 있으면 그 식당에 익힌 메뉴가 있는지 실제 메뉴를 확인하고 관련 회화도 준비
- **교통·비용** — 톨비, 주차비(1박 정액인지·출입 자유인지), 주유, 렌터카 서류. 조사한 비용은 버리지 말고 **예산 요약에 합산**
- **회화 문장** — 지어내지 말고 실제 쓰이는 표현인지 검색으로 확인. 존댓말 수준과 현지 관습까지

## 5. 동선 설계·일정 조립

`references/동선설계.md`대로 실행한다. 요지:

- **하루 3곳 기본, 상한 4곳.** 사전예약 필요 항목은 하루 1개까지. 이건 취향이 아니라 시설당 유효 집중이 30분~2시간이라는 물리적 상한에서 나온다
- **핀을 전부 찍고 뭉친 덩어리를 찾아** 그 구역에 반나절을 배정한다. 도심에서 먼 단독 명소는 전용일로 승격
- **제약이 클러스터링보다 우선한다** — 휴관일(월요일로 하드코딩 금지) → 슬롯형 예약 가능일 → 유효 폐관(표기 −60분) → 주방 닫힘 구간 → 유럽 일·월 조합
- **인기 스팟은 개장 직후.** 개문 시간을 확인하고 출발 시간까지 역산해 지정한다
- **이동시간은 폴백 사다리**로 산출하고 **타당성 필터를 무조건 적용**한다. 무료 라우팅 API가 커버리지 구멍에서 오답을 내기 때문이다(실측에서 4km 구간에 358분을 반환한 사례가 있다)
- **도착일은 야외·도보 위주로**, 앉는 활동과 최고 명소를 넣지 않는다
- **끼니 배정**: 하루 점심·저녁을 실제로 배정하되 ①카테고리 중복 금지 ②그날 동선 위에 있을 것 ③예약 필요 표시 ④만석·휴무 대비 백업 1곳. 배정 안 된 곳은 "골라먹는 후보"로 남긴다
- **쇼핑은 지역 클러스터로 묶어 도보 순서에 번호**를 붙인다
- **우천 플랜B**: 야외 위주인 날엔 실내 대체안을 1개 이상. 출발 직전 주간 예보를 확인해 반영
- **확정 안 된 건 "선택"**으로 붙이고, 현지에서 결정할 건 결정에 필요한 정보만 완비해 둔다
- **사용자가 정한 것을 임의로 바꾸지 않는다.** 더 나은 안이 있으면 이유와 함께 제안만 하고, 뒤집으면 즉시 따른다

## 5.5 일정 검산 ★

**`references/일정검산.md`대로 돌린다. 검산 없이 일정을 내밀지 않는다.**

일정표는 그럴듯해 보이기 쉽다. 장소는 잘 골랐는데 이동시간을 안 더했거나 폐관 시각을 안 봤으면 현장에서 무너진다. 하루를 시작 시각부터 분 단위로 누적해서 확인한다.

- 각 스팟마다: 개장 전 도착인가 · **유효 폐관(표기 −60분)** 안에 도착하는가 · 그 요일이 휴무인가 · 식사가 주방 닫힘 시간에 걸리는가
- 하루 끝: **막차 안에 숙소 복귀**가 되는가
- 하루 총량: 이동시간 합 · 도보 거리 합 · 스팟 수를 동행자 상한과 대조
- 대기 시간을 0으로 두지 않는다. 조사에서 "줄이 길다"는 언급이 있었으면 반영한다

걸리면 선택 항목 → 체류시간 → 순서 → 다른 날 → 스팟 제거 순으로 조정하고, **조용히 고치지 말고 고쳤다고 말한다.**

🔴 **검산 통과를 "검증됐다"고 말하지 않는다.** 이건 일관성 검사지 사실 검증이 아니라서, 영업시간을 잘못 읽었으면 그 잘못된 값으로 계산해서 통과시킨다. 사실 쪽은 5.7 납품 관문이 담당한다. 정확한 표현은 "시간축으로 돌려서 서로 안 부딪히는 건 확인했고, 개별 정보는 출처 링크로 남겨뒀다"이다.

검산 결과는 **하루 한 줄 요약**으로 보여준다. "09:00 출발 → 복귀 19:40 · 이동 1시간 50분 · 도보 3.2km · 3곳" 같은 줄이 제대로 계산했다는 증거다.

⚠️ 하루 도보량 상한은 신뢰할 출처가 없다. **임의 숫자를 만들지 말고 계산값을 보여주고 사용자 판단을 받는다.**

## 6. 아티팩트 제작

**`assets/template.html`의 구조·스타일 그대로** 내용만 채운다. 핵심 사양:

- 상단 고정 헤더: 여행 제목·날짜·인원·숙소·예약번호 + **글자 크기 토글** + 탭 5개(📅 일정 / 🧳 준비 / 🍽️ 식당 / 🛍️ 쇼핑 / 🗣️ 회화)
- **일정 탭**: 날짜별 카드. 각 날에 ①한 줄 요약 ②**검산 스탯 바**(`.stats`) ③시간표 행(시간/활동/메모/주소·전화) ④**대안 pill**(`.alts`). 주소는 복사용 텍스트 + `🗺️ 지도` 링크를 **항상 병기**. 하단에 **💰 예산 요약**(계산은 코드로)
  - **검산 스탯 바는 5.5에서 계산한 값을 그대로 옮긴다** — 출발·복귀·이동시간·도보km·스팟수. 이 줄이 "실제로 계산했다"는 유일한 시각 증거다. **값을 지어내지 않는다.** 계산 안 했으면 스탯 바를 넣지 않는다
  - **대안 pill은 그 날에 실제로 필요한 것만** 남긴다. ☔는 야외 비중이 높은 날, 🈳는 예약 없이 가는 식당이 있는 날. 내용 없이 자리만 남기지 않는다
  - **마지막 날 카드**는 시간표 맨 위에 **체크아웃 행과 짐 보관 행**을 두고, 스탯 바의 `복귀`를 `공항`으로 바꿔 하드 마감을 넣는다 (`references/숙소역산.md` 2-1절)
- **준비 탭**: 출발 전 D-day 체크리스트. **"D-30"이 아니라 실제 날짜로** 쓴다. 맨 위에 "제일 급한 것" 한 줄(여권 갱신 필요 등), 시점별 섹션, 🎒 챙길 것. **예약 오픈일이 정해진 명소는 반드시 여기에 날짜로 박는다**
- **식당·쇼핑 탭**: 체크박스 리스트. **체크 키(data-k)는 순번이 아니라 내용 기반 슬러그**(예: `f-ichiran-dotonbori`). 재발행 시 항목이 추가·이동돼도 **기존 키를 절대 바꾸지 않는다** — localStorage 체크가 키에 붙어 있어서 키가 바뀌면 여행 중 체크한 게 유실된다
- **회화 탭**: 상황별(교통·숙소·식당·쇼핑·편의점·긴급) 한국어/현지어/한글 발음 3줄 + **🚨 긴급 정보**(현지 긴급전화, 영사콜센터 +82-2-3210-0404, 보험 메모, 병원 찾는 법). 예약 전화가 필요한 식당이 있으면 **`references/예약키트.md`대로 "예약 전화" 섹션을 따로 두고** 날짜·시간·인원·이름을 채운 완성 문장으로 넣는다. 알레르기가 있으면 **현지어 알레르기 카드**를 만들되 중증 위험 경고를 반드시 붙인다
- 🔴 **재발행 프로토콜 — URL은 저절로 유지되지 않는다.** 여행은 며칠에 걸치므로 반드시 여러 세션이 되는데, **발행한 적 없는 세션에서 재발행하면 Artifact 도구는 무조건 새 URL을 발급한다.** 기존 것을 겨냥하는 방법은 `url` 파라미터뿐이다. 그래서:
  1. **최초 발행 직후** 아티팩트 URL과 HTML 파일 절대경로(`$TRIP_DIR/일정.html`)를 `$TRIP_DIR/여행노트.md`에 적는다
  2. **새 세션의 첫 동작**은 그 노트를 읽는 것. 노트가 없으면 `Artifact action:"list"`로 해당 여행 아티팩트를 찾는다
  3. **재발행 시 `url=<찾은 URL>`을 반드시 전달**한다. 같은 파일 경로만으로는 부족하다
- **"링크 그대로"는 `url` 전달에 성공했을 때만 말한다.** 새 URL이 발급됐으면 그 사실을 먼저 알린다 — 동행자에게 이미 보낸 링크가 죽었다는 뜻이므로 숨기면 안 된다
- **동행자 공유**: 발행 직후 **공유(share)를 켜야** 상대가 열린다는 걸 안내한다. 체크는 기기별 저장이라 자동 동기화가 안 되므로, 템플릿의 **`체크 내보내기` / `가져오기`** 버튼을 알려준다 — 코드를 복사해 보내면 상대 쪽에서 합쳐진다(합집합이라 서로 덮어쓰지 않는다). 역할 분담도 함께 제안한다
- **오프라인**: 이 템플릿은 외부 리소스를 하나도 안 쓰므로 **한 번 연 뒤에는 비행기 모드에서도 그대로 동작한다.** 지도 링크만 인터넷이 필요하다. 출국 전 폰에서 한 번 열어두라고 안내하고, 원하면 PDF 백업본도 만들어 준다
- **현장 대응**: 각 날 카드 하단에 **대안 한 줄**을 반드시 넣는다 — 비 올 때 갈 실내 한 곳, 그 날 배정 식당이 만석·휴무일 때 갈 백업 한 곳. 여행 중 "지금 어떡하지"가 생기는 지점이 이 둘이고, 현장에서 다시 물어보게 하지 않는 게 목표다

## 7. 피드백 루프 — 상담으로 되돌아가는 단계

**수정 요청은 단순 수정이 아니라 선호 신호다.** 반영하고 끝내지 말고 0번으로 돌아간다.

- 사용자가 뭘 **뺐으면** 그 카테고리 전체를 줄이고, 뭘 **추가했으면** 같은 종류를 더 찾아 제안한다
- 한 번 읽은 선호는 **남은 날 전체에 소급 적용**한다. 같은 지적을 두 번 하게 만들면 안 된다
- 수정 후 재발행은 6절 재발행 프로토콜대로(`url` 전달). 바뀐 것만 짧게 요약. **기존 항목의 data-k는 건드리지 않는다**
- 새 링크가 오면 2~4를 반복해 기존 분류에 병합 (중복은 새로 만들지 말고 기존에 보강)
- 여행 관련 파생 질문(주차비 기준, 터미널 위치, 축제 갈까, 예산 얼마)도 이 스킬 범위다. 답만 하지 말고 아티팩트에 반영할지 판단한다
- 대화가 길어지면 중간중간 "최종 정리"를 제공 (전체 일정 + 배정 + 예산 + 미결사항)

## 8. 🧭 여행 중 모드 — 현장에서 계획이 깨졌을 때

**출발 전 설계와 완전히 다른 모드다.** 여기서 필요한 건 완벽한 재설계가 아니라 **1분 안에 나오는 답**이다. 사용자는 지금 길 위에 서 있고, 데이터는 로밍이고, 동행자가 기다리고 있다.

**트리거**: "지금 뭐 하지" · "비 온다" · "줄이 두 시간이래" · "여기 문 닫았는데" · "시간이 남았어" · "애가 잠들었어" · "생각보다 일찍 끝났어"

### 이 모드의 규칙

1. **조사를 새로 시작하지 않는다.** 후보는 이미 필요량의 1.5~2배를 찾아뒀다(`실조사.md`). `$TRIP_DIR/조사결과.md`에서 **꺼내 쓰는 것**이 기본이다
2. **묻는 건 최대 셋.** 지금 몇 시인지 · 지금 어디인지 · 언제까지 자유인지. 하나라도 대화에 이미 있으면 안 묻는다
3. **새 fetch는 "지금 열려 있나" 확인 하나뿐이다.** 제안하려는 곳의 영업 여부만 그 자리에서 본다. 그 외의 조사는 지금 하지 않는다
4. **아티팩트를 재발행하지 않는다.** 현장에서는 채팅 답이 빠르다. 반영은 그날 저녁이나 사용자가 요청할 때
5. **2~3안을 나란히 준다.** 하나만 주면 그게 안 맞을 때 다시 물어야 한다

### 절차

```
① 여행노트 + 조사결과 읽기        ← $TRIP_DIR (기억에 의존하지 않는다)
② 남은 후보 필터
     · 현재 위치에서 이동 가능한가 (남은 시간의 1/3 이내로 잡는다)
     · 동행자 제약 카드를 여전히 지키는가
     · 실내가 필요한 상황인가 (비·폭염·낮잠)
③ 지금 영업 중인지 확인            ← 유일하게 새로 여는 것
④ 2~3안 제시 — 각각 이동시간·소요·왜 이걸 골랐는지 한 줄
```

### 상황별

- **비** — 그 날 카드의 ☔ 대안이 1순위다. 이미 골라둔 것이라 검증이 끝나 있다
- **줄이 김** — 대기를 감수할 가치가 있는지 먼저 말하고(조사 때 나온 평판을 근거로), 아니면 근처 대체안. **되돌아올 수 있는지**도 같이 본다
- **문 닫음·폐업** — 그 자리에서 백업으로 교체하고, **조사결과 파일에 폐업 표시를 남긴다**. 남은 일정에 같은 곳이 또 있으면 같이 뺀다
- **시간이 남음** — 남은 후보 중 **가까우면서 짧은 것**을 고른다. 여기서 무리하면 다음 일정이 밀린다
- **아이가 잠듦·체력 소진** — 스팟을 늘리지 말고 **줄이는 쪽**을 먼저 제안한다. 남은 후보는 내일로 넘긴다
- **후보 풀이 비었음** — 그때만 새로 찾되 **반경을 좁혀 1곳만**. 현장에서 넓게 조사하면 답이 늦어 쓸모가 없다

### 로밍이 없을 수도 있다

사용자가 답을 못 받는 상황을 전제한다. 그래서 **출발 전에** 각 날 대안 pill을 채워두는 게 이 모드의 진짜 대비다. 현장 대응은 그 위의 보조 수단이다.

## 호출 예산 관리

이 스킬은 외부 호출을 많이 쓴다. 낭비하면 세션 중간에 예산이 말라 일정이 반쪽으로 끝난다.

- **WebSearch는 세션당 한도가 있다.** 고정 URL WebFetch를 우선하고, 검색은 후보를 좁히거나 차단 플랫폼을 우회할 때만 쓴다. 한국처럼 검색이 유일한 경로인 나라는 예산을 아껴 배분한다
- **차단 플랫폼은 재시도하지 않는다.** OpenTable류는 60초 타임아웃이라 특히 비싸다
- 🔴 **공용 라우팅 API는 기본 경로가 아니다.** 조립 단계는 브라우저 Google Maps와 추정식으로 **외부 호출 0회**로 처리하고, 공용 API(OSRM·Transitous)는 최종 검산의 핵심 구간에만 **하루 10건 이내**로 쓴다. Transitous는 정책상 "여러 사용자로부터의 다수 요청" 전에 연락을 요구하므로 **사용자가 명시적으로 원할 때만** 쓴다
- **결과는 스크래치 파일에 캐싱**하고 같은 구간을 두 번 조회하지 않는다. Nominatim은 1 req/sec에 캐싱이 의무이고 User-Agent에 도구명과 연락 수단을 넣어야 한다
- 💀 **DuckDuckGo lite는 죽었다** — 2026-08 실측 기준 첫 요청부터 CAPTCHA다. 재시도하지 않는다. 차단 플랫폼 수치는 WebSearch `allowed_domains`로, 레딧은 Bash `old.reddit.com`으로 간다
