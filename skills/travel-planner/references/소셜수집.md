# 소셜 수집 — 유튜브·레딧·X·인스타에서 진짜 정보 긁어오기

리뷰 플랫폼은 **검증**에 강하고 소셜은 **발굴**에 강하다. "지금 사람들이 실제로 가는 곳", "관광객 함정이라는 경고", "작년에 폐업했다는 제보"는 타베로그가 아니라 유튜브 챕터와 레딧 댓글에 있다.

**둘 다 쓴다.** 소셜에서 후보를 발굴하고, 플랫폼에서 영업시간·휴무·전화를 확정한다. 순서를 바꾸면 안 된다 — 소셜 정보는 부정확하고 오래됐을 수 있다.

## 0. 실측 요약

| 소스                        | 경로                                                        | 판정                                        |
| :-------------------------- | :---------------------------------------------------------- | :------------------------------------------ |
| **유튜브 검색**             | `yt-dlp "ytsearch10:<쿼리>" --flat-playlist --dump-json`    | ✅ API 키 불필요. 조회수·길이·URL           |
| **유튜브 챕터·설명란**      | `yt-dlp --skip-download --dump-json <URL>`                  | ✅ **가장 정확.** 상호명 + 공식 사이트 링크 |
| **유튜브 자동자막**         | `yt-dlp --skip-download --write-auto-sub --sub-lang "en.*"` | ✅ whisper 불필요. 단 고유명사 뭉개짐       |
| **레딧 스레드**             | `old.reddit.com/...` **Bash에서 curl·urllib**               | ✅ 본문·댓글·점수 전부                      |
| 레딧 (WebFetch 도구)        | `reddit.com`                                                | ❌ 도구 레벨 차단                           |
| 레딧 JSON API               | `reddit.com/r/x/top.json`                                   | ❌ 403                                      |
| **X 개별 트윗**             | `x.com/<user>/status/<id>` 직접 fetch                       | ✅ 본문 읽힘                                |
| X 검색 페이지               | `x.com/search?q=`                                           | ❌ JS 셸 ("JavaScript is not available")    |
| **인스타 개별 릴스·게시물** | `instagram.com/reel/<code>/` 을 **WebFetch로**              | ✅ 캡션 전문·계정·해시태그·게시일           |
| 인스타 (Bash curl)          | 같은 URL을 curl·urllib으로                                  | ❌ 9자 껍데기 — **도구에 따라 갈린다**      |
| 인스타 임베드               | `/embed/captioned/`                                         | ❌ 껍데기 (예전 우회로였으나 지금은 막힘)   |
| 인스타 해시태그·탐색        | `instagram.com/explore/tags/`                               | ❌ JS 셸                                    |

**핵심 발견 둘**: 레딧은 사이트가 막은 게 아니라 **WebFetch 도구가 막는 것**이라 Bash로 우회된다. X는 검색이 막혔을 뿐 **개별 트윗 URL은 열린다**.

## 1. 유튜브 — 가장 수확이 큰 소스

### 1-1. 영상 찾기

```bash
yt-dlp --flat-playlist --dump-json "ytsearch8:tokyo best food guide 2026" 2>/dev/null
```

JSON으로 제목·조회수·길이·URL이 나온다. 고를 때 기준:

- **조회수가 높은 것** — 검증된 정보일 확률이 높다
- **최근 것** — 2년 넘은 영상은 폐업·가격변동 위험. 제목의 연도 표기를 본다
- **길이 20분 이상** — 짧은 영상은 스팟 2~3개뿐이다. 긴 가이드 영상 하나가 짧은 것 열 개보다 낫다
- **여행지+카테고리로 쿼리를 나눈다** — `tokyo food guide`, `tokyo hidden gems`, `tokyo with parents`, `<지역명> local eats`

상담 결과를 쿼리에 넣는다. 부모님 동행이면 `tokyo travel with elderly parents`, 아이 동반이면 `tokyo with kids`가 완전히 다른 영상을 준다.

### 1-2. ★ 챕터와 설명란이 자막보다 정확하다

```bash
yt-dlp --skip-download --dump-json "<영상URL>" 2>/dev/null
```

여기서 `chapters`와 `description`을 꺼낸다. **음식 가이드 영상은 챕터 제목이 그대로 가게 이름이다.**

실측 예 (도쿄 음식 가이드 영상 하나):

```
챕터 25개 = 가게 25곳
  0:36  Shinpachi Shokudō
  1:21  SHIBUichi BAKERY
  3:24  Ichikawa Tempura
  ...
설명란: "Food & Places (in order):" 아래 상호 + 공식 사이트 URL 전부
```

**설명란에 공식 사이트 링크가 있으면 그게 최고의 팩트체크 소스다.** 영업시간을 그 사이트에서 바로 확정할 수 있다.

설명란에서 촬영 시점도 확인한다. 위 영상은 "Filmed on October 9 to 17, 2024 (prices as of date of filming)"라고 명시했다 — **가격 정보의 유효기간을 판단하는 근거**다.

### 1-3. 자막 전사 — 맥락과 평가를 얻는다

```bash
yt-dlp --skip-download --write-auto-sub --sub-lang "en.*" --sub-format vtt -o "%(id)s" "<URL>"
```

한국어 영상이면 `--sub-lang "ko.*"`. VTT는 타임코드와 중복 줄이 많아 정제해야 한다 (실측에서 246KB VTT → 26KB 텍스트).

```python
import re
t = open(vtt, encoding='utf-8').read()
t = re.sub(r'<[^>]+>', '', t)
lines = [l.strip() for l in t.split('\n')]
lines = [l for l in lines if l and '-->' not in l
         and not l.startswith(('WEBVTT','Kind:','Language:'))]
out = []
for l in lines:
    if not out or out[-1] != l: out.append(l)      # 중복 제거가 핵심
txt = re.sub(r'\s+', ' ', ' '.join(out))
```

### ⚠️ 자동자막은 고유명사를 뭉갠다

실측 사례: "ski Tepanya"(→ Sky Teppanyaki 추정), "wagu"(→ wagyu). **자막에서 나온 가게 이름은 확정이 아니라 단서다.** 반드시 챕터·설명란과 대조하거나 플랫폼에서 검색해 실제 표기를 확정한다.

자막이 잘하는 것은 **평가와 맥락**이다. "여긴 줄이 길지만 30분이면 빠진다", "4,000엔인데 그만한 값어치는 없었다" 같은 판단이 여기 있고, 이건 플랫폼 점수에 안 나온다.

**whisper는 자동자막이 아예 없을 때만 쓴다.** 시간과 비용이 훨씬 크다.

## 2. 레딧 — 관광객 함정을 걸러내는 곳

레딧의 가치는 추천이 아니라 **반대 신호**다. "거긴 관광객만 간다", "작년에 주인 바뀌고 맛 없어졌다", "예약 안 받는다고 적혀 있는데 실제론 받는다" 같은 정보는 여기밖에 없다.

### 2-1. 스레드 찾기

WebFetch로는 못 가니 검색으로 URL을 확보한다.

```
https://lite.duckduckgo.com/lite/?q=site%3Areddit.com+<도시>+restaurant+recommendations
```

유용한 서브레딧: `r/<도시명>`, `r/JapanTravel` 같은 국가 여행 서브, `r/<나라>life`(현지 거주자), `r/finedining`.

### 2-2. 스레드 읽기 — Bash로

**WebFetch 말고 Bash에서** `old.reddit.com`을 친다. old 도메인은 서버 렌더라 댓글이 HTML에 다 있다.

```python
import urllib.request, re, html
UA = {'User-Agent': 'Mozilla/5.0 ... Chrome/126 Safari/537.36'}
h = urllib.request.urlopen(
        urllib.request.Request(url.replace('www.reddit','old.reddit'), headers=UA),
        timeout=30).read().decode('utf-8','replace')
bodies = re.findall(r'<div class="md">(.*?)</div>', h, re.S)
```

실측에서 스레드 하나에 댓글 22건과 추천 점수가 전부 나왔다.

**점수가 높은 댓글을 우선한다.** 점수는 `class="score unvoted"` 또는 JSON 조각에서 뽑는다. 레딧은 틀린 정보에 반박 댓글이 달리므로, 점수 높은 것만 보면 대체로 걸러진다.

### 2-3. 오래된 스레드 주의

검색으로 나오는 상위 스레드는 **몇 년 전 것일 때가 많다.** 스레드 날짜를 확인하고, 2년 넘었으면 거기 나온 가게는 반드시 플랫폼에서 현재 영업 여부를 확인한다.

## 3. X (트위터)

**검색 페이지는 JS 셸이라 못 읽는다.** 개별 트윗 URL은 읽힌다.

```
1) https://lite.duckduckgo.com/lite/?q=site%3Ax.com+<쿼리>   → status URL 확보
2) 그 status URL을 직접 fetch                                 → 본문 읽힘
```

실측에서 개별 트윗 하나가 2,795자로 읽혔고 "도쿄 야키니쿠 5곳" 같은 리스트 본문이 그대로 나왔다.

X는 **최신성**이 강점이다. 새로 연 곳, 이번 주 이벤트, 최근 가격 인상 같은 게 여기 먼저 뜬다. 반면 검증은 약하니 반드시 플랫폼으로 확인한다.

## 4. 인스타그램 — 링크를 안 줘도 찾아낼 수 있다

**한국 여행 콘텐츠가 가장 두껍게 쌓인 곳이다.** 한국인 여행 계정이 도쿄·오사카 맛집 리스트를 캡션에 통째로 적어두는 문화가 있어서, 한국어 검색으로 접근하면 수확이 크다.

### 4-1. 발견 — 검색으로 게시물을 찾는다

```
https://lite.duckduckgo.com/lite/?q=site%3Ainstagram.com+<도시>+맛집
https://html.duckduckgo.com/html/?q=site%3Ainstagram.com+<도시>+맛집
```

**스니펫에 캡션 전문이 실린다.** 실측에서 검색 결과 스니펫 하나에 가게 이름이 그대로 나열돼 있었다.

```
"할명수 도쿄편 맛집 추천 9 — 고다이메 하나야마우동 긴자점 / 하야시야신베에 /
 호카이반야 야키니쿠 / 팡메종 긴자점 / 긴자 돈카츠 사이토 / 쓰키시마 몬자야키 ..."
```

**게시물을 열지 않고도 후보 목록이 나온다.** 좋아요·댓글 수와 게시일도 스니펫에 실려서 신선도 판단까지 된다.

계정 자체도 찾아진다. 특정 도시 전문 계정(팔로워 수만 명대)을 발견하면 그 계정의 게시물을 더 파고들 수 있다.

### 4-2. 개별 게시물 — ⚠️ 반드시 WebFetch로

```
✅ WebFetch("https://www.instagram.com/reel/<code>/")   → 캡션 전문 나옴
❌ Bash에서 curl·urllib으로 같은 URL                     → 9자 껍데기
```

**같은 URL인데 도구에 따라 결과가 갈린다.** 레딧과 정반대다 — 레딧은 Bash로 뚫고 인스타는 WebFetch로 뚫는다. 헷갈리면 둘 다 못 쓴다.

실측에서 나온 필드: 계정명 · **캡션 전문** · 해시태그 · 위치태그 · 게시일 · 좋아요·댓글 수. 릴스에서 가게 이름 다섯 곳(츠지한·야마초·이치란·긴자비어홀·몬자야키)이 그대로 뽑혔다.

### 4-3. ⚠️ 한글 음차를 확정 표기로 쓰지 않는다

인스타 캡션은 한국인이 쓴 것이라 가게 이름이 **한글 음차**로 적혀 있다. "츠지한"은 실제로 `つじ半`이고, 이걸로 타베로그를 검색하면 못 찾는다.

유튜브 자막이 고유명사를 뭉개는 것과 같은 문제다. **음차는 단서일 뿐이고, 플랫폼에서 실제 표기를 확정해야 한다.** 위치태그와 해시태그가 힌트가 된다.

### 4-4. 여전히 안 되는 것

- **해시태그·탐색 페이지는 JS 셸**이다. 반복 fetch해봐야 안 나온다
- **슬라이드 이미지 안의 텍스트**는 캡션에 없다. 캐러셀은 `references/인스타추출.md`의 브라우저 파이프라인으로 슬라이드를 넘겨야 한다
- 임베드 엔드포인트(`/embed/captioned/`)는 예전 우회로였으나 지금은 막혔다

사용자가 링크를 직접 던진 경우는 **이미 사용자가 원하는 것**이므로 최우선으로 다루고, `인스타추출.md` 파이프라인을 끝까지 돌린다.

## 5. 수집한 것을 어떻게 쓰는가

### 소셜 → 플랫폼 → 일정 순서를 지킨다

```
소셜에서 발굴          "이 유튜버가 12곳 추천, 레딧에서 그중 2곳은 관광객 함정이라 함"
   ↓
플랫폼에서 확정        타베로그에서 실제 표기·점수·영업시간·정기휴무·전화 확인
   ↓
상담 조건으로 필터     어르신 동행이니 좌식·대기 긴 곳 제외
   ↓
동선으로 배치          그날 클러스터에 맞는 것만
```

**소셜 정보를 그대로 일정에 넣지 않는다.** 이름이 뭉개졌을 수 있고, 폐업했을 수 있고, 영업시간이 바뀌었을 수 있다.

### 교차 신호를 우대한다

**여러 소스에 동시에 나온 곳**이 가장 안전하다. 유튜브 챕터에도 있고 레딧 상위 댓글에도 있고 플랫폼 점수도 높으면 거의 확실하다. 반대로 한 소스에만 나오고 플랫폼에서 안 잡히면 의심한다.

### 출처를 남긴다

조사 결과 테이블에 **어느 영상·어느 스레드에서 나왔는지** 적는다. 사용자가 "이건 왜 넣었어?"라고 물으면 "조회수 52만 도쿄 음식 가이드 영상에서 추천했고 레딧에서도 언급됐다"고 답할 수 있어야 한다.

## 6. 하지 말 것

- **자막에서 뽑은 가게 이름을 그대로 확정하는 것** — 고유명사가 뭉개진다
- **인스타 캡션의 한글 음차를 실제 상호로 쓰는 것** — "츠지한"으로는 타베로그에서 못 찾는다
- **인스타를 Bash curl로, 레딧을 WebFetch로 여는 것** — 정반대다. 인스타=WebFetch, 레딧=Bash
- 소셜 정보를 플랫폼 검증 없이 일정에 넣는 것
- 오래된 레딧 스레드의 정보를 현재 사실로 쓰는 것
- 조회수만 보고 고르는 것 — 촬영 시점을 반드시 확인한다
- X 검색 페이지나 인스타 해시태그 페이지를 반복 fetch하는 것 (JS 셸이라 영원히 안 나온다)
- **로그인이 필요한 곳에 로그인을 시도하는 것.** 사용자 계정으로 열 때는 읽기만 한다
