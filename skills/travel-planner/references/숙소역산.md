# 숙소 역산 — 비행기표 한 장에서 후보 호텔 목록까지

사용자가 항공권만 던져도 첫날 밤 제약과 숙소 동네를 산출하고, **그 동네의 실제 호텔 후보를 뽑아 사용자가 고르게** 할 수 있다.

산출 순서가 중요하다.

```
항공권 → 첫날 밤 제약 → 동네 2~3곳 (Claude가 판단)
       → 각 동네의 호텔 후보 (trip.com에서 실제로 가져옴)
       → 3~5곳 비교표 (리조트피 포함) → 사용자가 선택
       → 선택된 숙소 기준으로 전체 동선 재계산
```

**숙소는 Claude가 확정하지 않는다.** 취향과 예산이 갈리는 영역이라, 근거를 붙인 후보를 내밀고 사용자가 고르는 게 맞다. 다만 "알아서 찾아보세요"로 넘기지도 않는다 — 후보는 실제로 뽑아준다.

한 가지는 여전히 못 한다. **"이 호텔이 최저가"는 말할 수 없다.** 한 페이지에 10~12건만 나오는 랭킹 샘플이라 전체 시세를 훑은 게 아니다.

## 0. 먼저 알아야 할 것 — 뭐가 뚫리고 뭐가 막혔나

## 1. 항공권에서 뽑는 것

사용자가 e-티켓 이미지나 "OZ102 8월 12일" 같은 한 줄만 줘도 된다.

```
https://www.trip.com/flights/status-<편명소문자>/
예: https://www.trip.com/flights/status-oz102/
```

실측에서 이 페이지 하나로 ICN 제2터미널 → NRT 제1터미널, 기종 A380-800, 정시율 87%까지 나왔다.

### ⚠️ 시각은 믿지 말 것

trip.com이 주는 건 **조회 시점의 스케줄**이다. 실측에서 같은 편명을 두고 trip.com은 08:25→10:50, 웹검색은 09:01→11:20으로 서로 다르게 보고했다.

**터미널과 공항은 자동 도출해도 되지만, 시각은 사용자 e-티켓 원문을 신뢰한다.** 사용자가 시각을 안 줬으면 물어본다. 추정한 시각으로 첫날 일정을 짜면 안 된다.

Wikipedia 공항 문서는 얼라이언스 단위(ANA=T1 South, JAL=T2)까지만 있고 개별 항공사 배정이 없어서 보조 자료로만 쓴다. 공항 공식 사이트는 대부분 403이다.

## 2. 첫날 밤 제약 판정

이게 숙소 위치를 가르는 첫 갈림길이다.

```
도착시각
  + 입국심사·수하물 60~90분      ← 공항·시즌에 따라. 성수기 대형 허브는 90분
  = 공항 출발 실질시각
  + 공항→도심 소요 (아래 소스로 확인)
  = 도심 도착 시각
```

도심 도착이 늦으면 (대중교통 막차 이후이거나 체크인 마감을 넘기면) **첫날 밤만 공항 인근에 잡고 다음날 도심으로 옮기는 안**을 제시한다. 짐을 두 번 옮기는 비용과 심야 택시비를 비교해서 사용자에게 판단 재료를 준다.

공항→도심 소요는 공식 관광청·교통 안내 페이지에서 확인한다. 예를 들어 japan-guide.com은 나리타 익스프레스 60분 ¥3,140, 스카이라이너 55분 ¥2,510, 리무진버스 100분 ¥3,100을 터미널별 운행 정보와 함께 준다.

## 2-1. ★ 출발일 역산 — 마지막 날을 통째로 비워두지 않는다

**도착 방향만 계산하고 끝내면 여행의 마지막 날이 미설계로 남는다.** 3박4일이면 4일 중 하루, 4박5일이면 5일 중 하루다. 그날 아침에 사용자는 "캐리어 끌고 어디까지 갈 수 있나"를 혼자 계산하게 된다.

**뒤에서부터 역산한다.**

```
출발 시각 (e-티켓 원문)
  − 국제선 공항 도착 권장 2~3시간     ← 항공사·공항 공식 안내로 확인. 임의로 정하지 않는다
  = 공항 도착 마감
  − 숙소·마지막 스팟 → 공항 소요       ← 동선설계 폴백 사다리로 산출
  = 그 지역을 떠나야 하는 시각          ← 이게 마지막 날의 하드 마감이다
```

여기에 **체크아웃 시각**(대부분 10~11시, 숙소 확정 후 실제 값 확인)을 얹으면 그날의 구조가 나온다.

```
체크아웃 → [짐을 어디 두는가] → 자유 시간 → 그 지역 떠남 → 공항
```

### 짐이 마지막 날의 전부를 결정한다

캐리어를 끌고 다니면 갈 수 있는 곳이 확 줄어든다. 그래서 **짐 처리를 먼저 정하고 그다음에 일정을 넣는다.** 선택지는 셋이다.

| 선택지          | 확인 경로                                                     | 주의                                                               |
| :-------------- | :------------------------------------------------------------ | :----------------------------------------------------------------- |
| **숙소 보관**   | 호텔 공식 사이트·전화로 **체크아웃 후 보관 가능 여부**를 확인 | 가장 확실하지만 저녁에 숙소로 되돌아와야 한다. 동선이 왕복이 된다  |
| **역 코인로커** | 브라우저 구글맵 또는 역 공식 사이트                           | 🔴 **대형 사이즈는 아침에 다 찬다.** 캐리어가 크면 못 넣을 수 있다 |
| **보관 서비스** | ecbo cloak 등                                                 | 🔴 **JS 셸이라 우리가 못 읽는다.** 링크만 넘기고 예약은 사용자가   |

🔴 **짐 보관 가능 여부를 실측 못 했으면 `미확인`으로 표시한다.** "코인로커 있습니다"를 근거 없이 쓰지 않는다 — 그날 아침에 캐리어를 못 맡기면 일정 전체가 무너진다.

### 마지막 날 일정 규칙

- **하드 마감 안쪽으로만** 넣는다. 스팟 수는 평소보다 한 곳 줄인다
- **짐을 맡긴 곳 근처**나 **공항 가는 길 위**에 배치한다. 반대편은 아예 후보에서 뺀다
- **예약이 필요한 곳·줄이 긴 곳을 넣지 않는다.** 여기서 밀리면 비행기를 놓친다
- 공항에서 할 수 있는 것(면세·라운지·마지막 식사)은 시간이 남을 때의 대안으로만 둔다
- **출국 심사가 오래 걸리는 공항**은 그 사실을 먼저 알린다

이 계산 결과는 아티팩트 마지막 날 카드에 **체크아웃 행과 짐 보관 행으로 명시**한다. 시간표 위쪽에 둬서 아침에 제일 먼저 보이게 한다.

## 3. trip.com 호텔 데이터 — 뽑히는 것과 한계

```
https://www.trip.com/hotels/list?city=<cityId>&checkin=YYYY-MM-DD&checkout=YYYY-MM-DD
https://www.trip.com/hotels/detail/?hotelId=<id>
```

**WebFetch로 열면 호텔 12곳이 이렇게 나온다** (실측):

```
The Tourist Hotel & Cafe Akihabara | $125 | 9.2/10 | Kanda | 8 mins walk to central Akihabara
KOKO HOTEL Shinjuku Yotsuya      |  $92 | 8.7/10 | Shinjuku Area
lyf Shibuya Tokyo                | $157 | 9.5/10 | Shibuya | 4 mins walk to Shibuya Center-Gai
...
```

이름 · 가격 · 평점(10점 만점) · 동네 · **"N mins walk to 〇〇"** 가 세트로 나온다. 마지막 항목이 캐리어 이동의 직접 지표라 가장 쓸모 있다. 상세 페이지(`/hotels/detail/?hotelId=`)는 여기에 정확한 주소와 공항까지 거리를 더해준다.

### 🔑 city ID 찾기 — 검색 한 번이면 된다

ID를 추측하지 않는다. **웹 검색으로 slug URL을 찾으면 ID가 URL 안에 박혀 있다.**

```
검색: trip.com "hotels-list" <도시명>
결과: https://www.trip.com/hotels/honolulu-hotels-list-757/   ← 757이 city ID
```

**slug URL은 자기검증이 된다.** slug와 ID가 맞지 않으면 **404**가 난다. 실측:

```
✅ /hotels/honolulu-hotels-list-757/   → 200 "10 Best Honolulu Hotels…"
✅ /hotels/tokyo-hotels-list-228/      → 200 "10 Best Tokyo Hotels…"
❌ /hotels/osaka-hotels-list-347/      → 404  (347은 오사카가 아니라 로스앤젤레스)
```

즉 **200이 뜨면 ID가 맞는 것**이다. 별도 검증 단계가 필요 없다.

확인된 ID 몇 개: 도쿄 228 · 호놀룰루 757 · 방콕 359 · 상하이 2 · 로스앤젤레스 347.

### 🔑 zone으로 동네를 좁힌다

`?city=` 형식은 `keyword=`를 무시해서 동네 필터가 안 되지만, **slug URL에는 zone 경로가 붙는다.**

```
https://www.trip.com/hotels/<slug>-hotels-list-<ID>/zone<zoneId>/
```

zone ID도 같은 검색에서 함께 나온다. 호놀룰루 실측:

| zone            | 지역              |
| :-------------- | :---------------- |
| `zone2828`      | **와이키키**      |
| `zone2827`      | 다운타운 호놀룰루 |
| `zone14640`     | 공항 인근         |
| `zone107183010` | 이스트 호놀룰루   |

와이키키 zone을 열면 **그 동네 호텔만 10곳**이 나온다 (실측):

```
Prince Waikiki                        9.0/10   $204
Halepuna Waikiki by Halekulani        9.2/10   $365
Hyatt Regency Waikiki Beach Resort    8.7/10   $279
Alohilani Resort Waikiki Beach        8.3/10   $326
Hilton Hawaiian Village               8.2/10   $230
Waikiki Resort Hotel                  8.3/10   $130
Kuhio Banyan                          8.7/10    $69
FIRST CABIN INTERNATIONAL HAWAII      9.0/10    $85
Royal Grove Waikiki                   7.9/10    $80
Queen Kapiolani Hotel                 8.8/10      —
```

**이게 사용자에게 내밀 후보 목록이다.** 동네를 먼저 정하고 그 동네 zone에서 후보를 뽑으면, 추천 근거(동네)와 선택지(호텔)가 분리돼서 사용자가 고르기 쉬워진다.

### 반드시 지킬 것

1. **한 페이지에 10~12건만 나온다.** trip.com 랭킹의 샘플이지 전체 검색 결과가 아니다. "최저가"라고 말하면 안 된다.
2. **평점은 10점 만점**이다. 5점 척도로 오독하지 않는다.
3. **가격은 시세 감**이다. 날짜·객실 조건에 따라 달라지므로 "1박 $200대"처럼 밴드로 말한다.
4. 🔴 **리조트피와 주차비가 여기 안 나온다.** 다음 절 참고 — 이걸 빠뜨리면 예산이 크게 틀어진다.

## 3-1. ★ 후보를 뽑아서 사용자가 고르게 하는 절차

숙소는 취향과 예산이 갈리는 영역이라 **Claude가 하나로 확정하지 않는다.** 근거를 붙인 후보를 내밀고 사용자가 고른다.

**① 동네를 먼저 좁힌다** — 아래 4절의 네 축(첫날 밤 제약·일정 무게중심·교통 허브·캐리어 이동)으로 동네를 2~3곳으로 줄인다. 이 단계는 Claude가 판단한다.

**② 각 동네 zone에서 후보를 뽑는다** — 위 zone URL로 그 동네 호텔 목록을 가져온다.

**③ 3~5곳으로 추린다** — 전부 보여주면 고르기 어렵다. 상담에서 나온 조건으로 거른다. 신혼부부면 평점 8.5 이상 + 오션뷰 가능 여부, 아이 동반이면 수영장과 객실 크기, 예산 우선이면 가격순.

**④ 비교표로 제시한다** — 사용자가 한눈에 비교할 수 있어야 한다.

```
| 호텔 | 동네 | 평점 | 1박 | 특징 | 리조트피 |
|:--|:--|--:|--:|:--|--:|
| A | 와이키키 | 9.2 | $365 | 해변 도보 2분, 조용함 | 없음 |
| B | 와이키키 | 9.0 | $204 | 가성비, 박물관 무료 혜택 | $45 |
| C | 다운타운 | 8.7 | $150 | 저렴, 해변까지 차 10분 | $0 |
```

각 후보에 **왜 이걸 골랐는지 한 줄**을 붙인다. 그리고 **트레이드오프를 숨기지 않는다** — "제일 싸지만 해변에서 멉니다"까지 말해야 사용자가 판단할 수 있다.

**⑤ 예약 링크를 함께 준다** — 조건이 채워진 booking.com 링크(6절)나 trip.com zone URL을 붙여서 바로 넘어갈 수 있게 한다.

**⑥ 고른 뒤에 일정을 다시 계산한다** — 숙소가 정해지면 그게 모든 동선의 기준점이 된다. 각 날의 이동시간을 그 좌표 기준으로 다시 산출하고, 필요하면 `일정검산.md`를 다시 돌린다.

## 3-2. 🔴 리조트피 — trip.com 가격에 안 들어 있다

**표시 가격만 보고 예산을 잡으면 크게 틀어진다.** 리조트 지역은 객실료와 별개로 매일 붙는 요금이 있다.

하와이 와이키키 실측 (호텔 공식 사이트):

| 호텔                    | 리조트피/박 |    주차/박 |
| :---------------------- | ----------: | ---------: |
| Halekulani              |    **없음** |        $68 |
| Prince Waikiki          |         $45 |     $45~50 |
| Outrigger               |         $50 |        $60 |
| Royal Hawaiian          |         $52 |     $55~65 |
| Hilton Hawaiian Village |      미공개 | **$72~93** |

거기에 하와이는 숙박세 **18.712%**가 붙고 **리조트피에도 과세**된다. $50 리조트피가 실질 $59다.

**절차**: 후보를 3~5곳으로 추렸으면 **각 호텔 공식 사이트에서 리조트피와 주차비를 확인**해서 비교표에 넣는다. 호텔 FAQ 페이지에 대부분 있다. 못 찾으면 "미공개"로 표시하고 추측하지 않는다.

⚠️ **"리조트피 없음" 프로모션에 주의한다.** 홈페이지 배너로 걸어놓고 FAQ에는 정가가 적힌 경우가 있다(Outrigger 실측). 그 오퍼로 예약해야만 적용되니 조건을 확인하라고 알린다.

참고로 미국은 2025년 5월부터, 하와이는 2026년 7월부터 **광고 총액에 의무 수수료를 포함**하도록 규정이 생겼다. 다만 **세금은 총액에서 빠져도 합법**이라 표시가에 숙박세가 아직 안 붙어 있을 수 있다.

## 4. 동네를 좁히는 네 축

호텔 후보를 뽑기 **전에** 동네부터 정한다. 이 판단은 Claude가 하고, 호텔 선택은 사용자가 한다. 네 축으로 본다.

**① 첫날 밤 제약** — 위 2번. 늦은 도착이면 공항 인근 1박 분리를 검토한다.

**② 일정 무게중심** — 사용자가 가려는 곳들을 좌표화해서 중심점을 구한다. trip.com이 호텔마다 위도·경도를 주므로 후보 동네와의 거리를 정량 비교할 수 있다. 무게중심에서 먼 동네를 고르면 매일 왕복 이동시간이 붙는다.

**③ 교통 허브 등급** — 공항철도가 어느 역에 서는지, 주요 목적지까지 환승이 몇 번인지. 환승 0~1회 동네를 우선한다. 캐리어를 들고 두 번 갈아타는 건 지도상 거리와 무관하게 비싼 이동이다.

**④ 캐리어·안전·편의 밀도** — trip.com `positionDesc`의 "N mins walk to 〇〇 Station"이 캐리어 이동의 직접 지표다. 도보 10분이 넘으면 명시한다. 동네 성격은 공식 관광청의 권역 분류로 판정한다 (예: gotokyo.org는 5개 권역 49개 동네를 분류해 놓았다).

여기까지가 **동네 2~3곳 + 각각의 근거 + 트레이드오프**다. 이 다음에 3-1절로 가서 각 동네의 호텔 후보를 뽑는다.

## 5. 프리필 링크 핸드오프

실제 예약은 사용자가 한다. 봇은 막혀도 사람은 정상적으로 접속되므로, 조건이 채워진 링크를 건네는 게 최선이다.

```
# booking.com — 브라우저 로드 검증 완료
https://www.booking.com/searchresults.html?ss={동네}%2C+{도시}
  &checkin=YYYY-MM-DD&checkout=YYYY-MM-DD
  &group_adults=2&no_rooms=1&group_children=0

# Google Maps 장소·경로
https://www.google.com/maps/search/?api=1&query={역명}+{도시}
https://www.google.com/maps/dir/?api=1&origin={공항}&destination={역명}&travelmode=transit
```

booking.com 링크는 실제 브라우저에서 날짜·인원·지역이 정확히 파싱되는 걸 확인했고, 동네별 매물 수 필터까지 노출된다. agoda 파라미터는 검증하지 못했으니 확신 없이 제시하지 않는다.

## 6. 하지 말 것

- **"최저가"·"최적가" 약속 금지.** 10~12건 샘플로는 근거가 없다.
- **숙소를 Claude가 확정하지 않는다.** 후보를 뽑아 비교표로 내밀고 사용자가 고른다. 반대로 "직접 찾아보세요"로 넘기지도 않는다.
- **리조트피를 빠뜨리지 않는다.** trip.com 가격에 안 들어 있어서, 후보를 추린 뒤 호텔 공식 사이트에서 따로 확인한다. 이걸 놓치면 1박 $110가 통째로 빠진다.
- **city ID 추측 금지.** slug URL을 검색으로 찾는다. 200이 뜨면 맞고 404면 틀린 ID다.
- **차단 사이트 재시도 금지.** booking·agoda·Reddit·TripAdvisor는 스크래핑하지 말고 링크로만 전달한다. OpenTable류는 60초 타임아웃이라 특히 비싸다.
- **평점을 5점 척도로 오독 금지.** trip.com은 10점 만점이다.
- **도착 시각 추정 금지.** e-티켓 원문이 없으면 사용자에게 묻는다.

## 미검증으로 남은 것

각 도시 대중교통 막차 시각 · agoda 검색 파라미터 정합성 · NRT 외 공항(KIX·BKK·CDG·JFK 등)에서 외항사 터미널을 자동 확정하는 경로. 이 항목들은 사용자에게 확정 정보처럼 말하지 말고 공식 사이트 확인을 권한다.
