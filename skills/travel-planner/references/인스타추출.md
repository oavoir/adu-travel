# 링크 추출 파이프라인 (인스타 + 타 플랫폼)

여행 가기 전에 저장해둔 링크를 붙여넣는 건 이 스킬에서 **가장 흔한 진입 방식**이다. 링크에서 나온 것은 **사용자가 이미 가고 싶다고 결정한 곳**이라 다른 어떤 후보보다 우선순위가 높다.

링크를 받으면 이 순서대로 끝까지 시도한다. **사용자에게 스크린샷을 요구하는 선택지는 없다.** (사용자가 자발적으로 주면 활용)

## 0. 링크 뭉치를 받았을 때 — 먼저 할 것

**① 즉시 접수 확인을 한다.** 링크가 20개면 처리에 시간이 걸린다. 말없이 오래 작업하지 말고 "몇 개 받았고 지금부터 하나씩 열겠다"고 먼저 알린다.

**② 정규화하고 중복을 제거한다.**

- URL은 쿼리 파라미터를 떼고 정규형으로: `https://www.instagram.com/reel/CODE/` 또는 `/p/CODE/`
- 링크가 여러 개 붙어서 오면(공백 없이 이어진 경우도 있음) 전부 분리해 목록화
- 이미 처리한 링크인지 확인 — 같은 링크 재전송이면 기존 결과 재사용

**③ 여행 정보가 아직 없으면 지금 묻는다.** 링크만 오고 여행지·날짜·동행자를 모르는 상태라면 링크를 다 열어봐야 일정으로 못 만든다. `여행상담.md`의 네 가지를 먼저 확보한다. 다만 **링크 추출은 그 대화와 병행**해서 진행한다 — 사용자를 기다리게 하지 않는다.

**④ 링크가 여행지와 안 맞으면 바로 말한다.** 도쿄 간다면서 오사카 링크가 섞여 있으면 그때 확인한다. 다 처리한 뒤에 "이건 범위 밖입니다"라고 하면 시간을 버린 것이다.

## ⚠️ 대량 배치 생존 규칙 (링크 ≈10개 이상)

긴 세션에서는 앞쪽 대화가 요약되면서 초반 추출 결과가 날아갈 수 있다. **결과만 저장하는 걸로는 부족하다** — 링크 목록 자체가 대화에만 있으면, 요약된 뒤에 "몇 개가 남았는지"를 알 방법이 없다.

그래서 **결과 파일이 아니라 작업 큐 파일**을 쓴다.

### 절차

**1단계 — 큐를 먼저 만든다.** 링크를 하나라도 처리하기 전에, 받은 링크 전부를 파일에 박는다.

```bash
# $TRIP_DIR는 SKILL.md '작업 폴더'에서 이미 정해져 있어야 한다. 없으면 거기부터.
cat > "$TRIP_DIR/링크큐.tsv" <<'EOF'
대기	https://www.instagram.com/reel/AAA/
대기	https://www.instagram.com/reel/BBB/
EOF
```

**2단계 — 한 건 처리할 때마다 상태를 바꾸고 결과를 append**한다. 상태는 `대기` · `완료` · `실패` · `범위밖` 넷뿐이다.

```bash
# 상태 갱신 — sed -i는 macOS와 Linux 문법이 달라서 쓰지 않는다
python3 - "$TRIP_DIR/링크큐.tsv" "<URL>" 완료 <<'EOF'
import sys
p, u, st = sys.argv[1], sys.argv[2], sys.argv[3]
ls = open(p, encoding='utf-8').read().splitlines()
open(p, 'w', encoding='utf-8').write(
    "\n".join(f"{st}\t{u}" if l.split('\t')[-1] == u else l for l in ls) + "\n")
EOF

# 결과 누적
cat >> "$TRIP_DIR/추출결과.md" <<'EOF'
## <URL>
- 지역: 오사카 난바 | 분류: 식당 | 상호: …
- 출처 확인: <플랫폼 URL>
EOF
```

**3단계 — 진행 상황은 세지 말고 물어본다.** 기억에 의존하지 않는다.

```bash
cut -f1 "$TRIP_DIR/링크큐.tsv" | sort | uniq -c
```

**4단계 — 큐에 `대기`가 0이 될 때까지 끝내지 않는다.** 아티팩트 제작·병합·보고는 전부 **대화 기억이 아니라 이 두 파일을 읽어서** 한다.

### 왜 이렇게까지 하는가

컨텍스트 요약은 예고 없이 일어나고, 요약본은 "링크 20개를 받았다"까지만 남기고 **어느 20개인지는 남기지 않는다.** 큐 파일이 있으면 요약이 몇 번 일어나든 `uniq -c` 한 줄로 정확히 복구된다. 사용자에게 보고할 때도 이 집계를 그대로 쓴다 — "20개 중 17개 정리, 3개 실패"가 추정이 아니라 실측이 된다.

**중간에 링크가 추가로 오면 큐에 append**하고 같은 루프를 계속한다. 새 파일을 만들지 않는다.

## 1차: WebFetch (캡션 추출) — ⚠️ 반드시 WebFetch로

```
WebFetch(url, "Extract the caption, location, place names, shop names,
restaurant names, prices, and any travel tips. List everything mentioned.")
```

🔴 **Bash에서 curl로 열면 껍데기만 나온다.** 같은 URL인데 도구에 따라 결과가 갈린다. 2026-08-13 실측에서 curl은 200에 600KB를 주지만 `og:description`이 0건이었다 — **응답 크기로 성공을 판정하면 안 된다.** 캡션 텍스트가 실제로 잡히는지로 본다.

```
인스타 → WebFetch  ✅
인스타 → Bash curl ❌ (크기만 크고 캡션 없음)
```

실측에서 나오는 것: 계정명 · **캡션 전문** · 해시태그 · 위치태그 · 게시일 · 좋아요·댓글 수. 릴스 하나에서 가게 다섯 곳이 그대로 뽑힌 사례가 있다.

- 캡션에 정보를 다 적는 창작자가 많아서 이걸로 절반 이상 해결된다
- 결과가 "Instagram" 한 단어거나 빈 껍데기 → 2차로
- 캡션은 나왔는데 "자세한 건 영상/슬라이드에" 식이면 → 정보가 이미지에 있는 것. 2차로
- 주의: WebFetch는 15분 캐시라 같은 URL 재시도는 같은 결과. 바로 2차로 넘어갈 것

### 🔴 한글 음차를 확정 상호로 쓰지 않는다

한국 계정의 캡션은 가게 이름이 **한글 음차**로 적혀 있다. "츠지한"의 실제 표기는 `つじ半`이고, 음차로는 타베로그에서 검색이 안 된다. **음차는 단서일 뿐**이고 실제 표기는 그 나라 플랫폼(`국가별플랫폼.md`)에서 확정한다. 위치태그와 해시태그가 힌트가 된다.

## 2차: 브라우저 (슬라이드·화면 직접 보기)

**캐러셀(/p/)은 반드시 이 단계까지 와야 한다** — 정보가 슬라이드 이미지 안에 있는 게 기본이기 때문. 순서:

1. `navigate(url)` → `get_page_text` (부분 캡션 + 위치태그 + 계정명이 잡힘)
2. `read_page`로 구조 파악 → **"더 보기" 버튼**이 있으면 클릭해 캡션 전체 펼치기
3. **로그인 팝업 닫기**: 팝업의 X 버튼 클릭 → 안 되면 Escape → 안 되면 게시물 이미지 영역을 직접 클릭 (셋 중 하나로 닫힘)
4. `screenshot`으로 현재 슬라이드를 **눈으로 읽기** (슬라이드 속 텍스트·가게명·가격이 여기서 나옴)
5. 캐러셀이면 **오른쪽 화살표(다음)를 클릭 → screenshot**을 슬라이드 개수만큼 반복. 하단 점 개수로 총 슬라이드 수 파악. **전부** 넘겨볼 것 — 마지막 슬라이드에 매장 리스트·기간이 있는 경우가 많다
6. 릴스(/reel/)는 영상 프레임을 읽을 수 없다 → 캡션 전문 + 위치태그 + 썸네일 스크린샷까지 확보하고 3차로 보강

팁: read_page의 이미지 대체텍스트("문구: '...'의 이미지일 수 있음")에 슬라이드 속 글자가 일부 잡히기도 한다. 참고용으로 훑을 것.

## 2.5차: 로그인된 크롬 (Claude in Chrome — 있으면 최강 폴백)

인스타 로그인벽은 비로그인 브라우저에 자주, 세게 걸린다. **`mcp__claude-in-chrome__*` 도구가 이 세션에 있으면** 사용자의 실제 크롬(로그인 세션)으로 열 수 있어서 로그인벽 문제가 거의 사라진다:

- 도구가 deferred면 ToolSearch로 로드: `select:mcp__claude-in-chrome__tabs_context_mcp,mcp__claude-in-chrome__navigate,mcp__claude-in-chrome__computer,mcp__claude-in-chrome__read_page,mcp__claude-in-chrome__get_page_text`
- 사용자의 실계정으로 보는 것이므로 **읽기만** 한다 — 좋아요·팔로우·댓글 등 어떤 조작도 금지
- 2차와 같은 방식으로 슬라이드를 넘기며 스크린샷
- 도구가 없거나 사용자가 크롬 연결을 원치 않으면 건너뛰고 3차로

## 3차: 웹 교차검증 (유명 콘텐츠는 거의 다 뚫림)

영상 속 정보라 직접 못 읽는 경우, 확보한 단서(캡션 문구·계정명·위치태그·주제)로 웹 검색:

- **방송·유튜브발 콘텐츠** (또간집, 성시경 먹을텐데 등): "프로그램명 + 도시 + 맛집"으로 검색 → 정리 블로그·기사에 상호·주소까지 다 있음
- **공식 캠페인·한정 이벤트** (유니클로 UTme, 팝업스토어): 브랜드 공식 페이지에서 기간·대상 매장·조건을 원문으로 확정
- **가게 하나가 특정 안 될 때**: 캡션의 부분 정보(역 도보 X분, 메뉴, 가격)로 검색해 후보를 좁히고, 그 나라 맛집 플랫폼(`references/국가별플랫폼.md`)에서 실존 확인. **구글맵은 WebFetch로 안 읽히니** 필요하면 브라우저 도구로 연다
- 검색어는 한국어+현지어(일본어 등) 양쪽으로

## 4차: 그래도 안 되면

- "이 링크는 WebFetch·브라우저 슬라이드·(로그인 크롬)·웹 검색까지 시도했는데 [영상 안에만 정보가 있어서 / 계정이 비공개라] 못 뽑았다"고 **투명하게** 보고하고 미해결 목록에 남긴다
- 스크린샷을 요구하지 않는다. 단, 사용자가 먼저 스샷을 주면 즉시 읽어 반영
- 미해결이어도 대화 맥락에서 힌트가 오면(예: "그거 중고명품 가게야") 그 힌트로 3차를 재시도

## 인스타가 아닌 링크

사용자는 플랫폼을 가리지 않고 던진다. 원칙은 동일 — "전체 내용을 직접 확인":

- **유튜브·쇼츠**: `yt-dlp --skip-download --dump-json <URL>`로 **챕터와 설명란**을 뽑는 게 가장 정확하다. 음식 가이드 영상은 챕터 제목이 곧 가게 이름이고 설명란에 공식 사이트 링크가 붙어 있다. 자막 전사는 평가·맥락용이고 **고유명사가 뭉개지니** 확정 근거로 쓰지 않는다 (`소셜수집.md` 참고)
- **틱톡**: 인스타와 동일 파이프라인 (WebFetch → 브라우저 → 웹 검색)
- **네이버 블로그**: 🟢 **읽힌다 (2026-08-13 갱신).** 단 URL을 바꿔야 한다 — `blog.naver.com/<id>/<logNo>`는 프레임 셸이고, **`blog.naver.com/PostView.naver?blogId=<id>&logNo=<logNo>`로 Bash curl** 하면 본문이 통째로 나온다(실측 5,729자). `m.blog.naver.com/<id>/<logNo>`도 열린다. 추출할 때 `se-main-container` 안쪽만 자르지 않으면 네이버 UI 텍스트가 본문을 덮는다. 상세는 `국가별플랫폼.md` 2절
- **티스토리·브런치**: WebFetch로 읽힌다
- **지도 링크(구글맵·네이버지도 공유)**: 장소명만 추출해서 팩트체크 단계로 바로 넘긴다. 링크 자체는 WebFetch로 못 읽는다
- **레딧**: 💀 **2026-08-13부로 전 경로 사망.** 링크가 와도 못 읽는다 — 그 사실을 밝히고 제목에 담긴 가게 이름만 사용자에게 확인해 팩트체크로 넘긴다

## 추출 후 — 링크를 일정으로 바꾸는 절차

추출은 절반이다. 나머지 절반은 **이걸 일정에 녹이는 것**이고, 여기서 대부분의 가치가 나온다.

### ① 표로 먼저 보고한다

링크별로 무슨 내용인지, 어느 지역인지, 일정에 넣을 수 있는지를 표로 보여준다. 대량 배치면 `추출결과.md` 기준으로 집계한다. **사용자가 "내가 저장한 게 이렇게 정리되는구나"를 여기서 처음 느낀다.**

### ② 링크에서 나온 것을 최우선 배치한다

**이건 사용자가 이미 가고 싶다고 결정한 곳이다.** 플랫폼 랭킹 1위보다 우선한다. 일정의 뼈대를 링크 항목으로 먼저 세우고, 빈 곳을 백지 발굴(`실조사.md`)로 채운다.

### ③ 그래도 팩트체크는 한다

링크에서 나왔다고 검증을 건너뛰지 않는다. 릴스가 2년 전 것이면 폐업했을 수 있고, 영업시간이 바뀌었을 수 있다. **게시일을 확인**하고, 오래됐으면 현재 영업 여부부터 본다. 음차 상호는 실제 표기를 확정한다.

**🔬 실측 사례 (2026-08-06, 오사카 릴스 6개 → 18곳)** — 캡션을 그대로 믿었을 때 무엇이 틀리는지 보여준다.

**교훈 셋**

1. **릴스는 휴무와 결제수단을 거의 말하지 않는다.** 일정을 깨는 값이 정확히 그 둘이다
2. **검색 스니펫과 상세 페이지가 다를 수 있다.** 스니펫은 후보를 좁히는 용도지 확정 근거가 아니다
3. **캡션에 주소·전화가 있어도 플랫폼에 없으면 미확인이다.** 정보가 많다고 확인된 게 아니다

그래서 납품물에서는 **확정 / 캡션값만 / 못 찾음**을 반드시 나눠서 적는다. 섞어 놓으면 사용자가 무엇을 믿어야 할지 알 수 없다.

### ④ 범위 밖은 버리지 않는다

여행지에서 먼 곳이면 (a) 근처 대체 스팟을 찾아 제안하거나 (b) "다음 여행용"으로 저장한다. 어느 쪽인지 사용자에게 택일하게 한다. **말없이 빼면 사용자는 자기가 준 링크가 어디 갔는지 모른다.**

### ⑤ 기간한정은 즉시 대조한다

마감일과 여행 날짜를 바로 맞춰본다. 겹치면 ⚠️로 강조하고 **가능한 날을 역산해서 일정에 강제 배치**한다. 이미 지났으면 그 사실을 알린다.

### ⑥ 못 뽑은 링크를 숨기지 않는다

미해결 목록을 명시적으로 보여준다. "20개 중 17개 정리했고 3개는 영상 안에만 정보가 있어서 못 뽑았다"가 정직한 보고다. 사용자가 그 3개는 직접 알려줄 수도 있다.

### ⑦ 여행 중에 링크가 더 오면 병합한다

같은 아티팩트에 누적한다. **중복은 새로 만들지 말고 기존 항목에 정보를 보강**한다. 그리고 새 링크는 선호 신호이기도 하니(`여행상담.md` 5절) 남은 일정에 반영할지 판단한다.
